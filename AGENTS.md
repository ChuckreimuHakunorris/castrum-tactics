# Repository guidance

- The external project files directory is `D:\Game Projects\Files`. Inspect and import materials there only when the project owner requests them. Leave originals unchanged unless authorized, and keep local paths out of application code, builds, and CI.
- Use `scripts/Install-AndroidDebug.ps1` for routine Android debug deployments. Keep the standard package ID `com.castrumtactics.prototype` stable across milestone builds.

- Add meaningful XML documentation to new or changed public C# APIs. Include parameters, return values, exceptions, and behavioral constraints where applicable.
- Update the affected documentation with any change to a public API or documented behavior. Record milestone status in the [roadmap](Documentation/DevelopmentRoadmap.md) and accepted choices in the [decision log](Documentation/DecisionLog.md). Keep historical study results and their tested revisions intact.
- Run the [engineering checks](Documentation/EngineeringVerification.md#local-commands-and-ci) before review. Keep frozen sources and recorded evidence out of formatting changes and review [archive manifest changes](Documentation/EngineeringVerification.md#archive-integrity) explicitly.
- Follow the [visual development roadmap](Documentation/VisualDevelopmentRoadmap.md) and keep board visuals separate from authoritative match state.
- Follow the [documentation contributor guide](Documentation/contributing.md) when changing the site. Keep generated DocFX output out of version control.
- Use concise implementation comments to explain non-obvious calculations, important design decisions, invariants, and distinct logical phases of longer methods. Prefer comments that explain intent or reasoning rather than restating the code. Avoid unnecessary comments on straightforward operations.
- Follow [Session Architecture](Documentation/SessionArchitecture.md) when implementing gameplay, sessions, player input, AI, or multiplayer. Preserve the separation between presentation, session coordination, and authoritative domain rules.
- Follow [Main-Phase Rules and Architecture](Documentation/MainPhaseArchitecture.md) for the implemented domain rules and local session integration. Keep secured territory separate from physical piece ownership, derive legal moves from territorial classification without circular dependencies, and validate both players against one pre-turn snapshot. Inaccessible terrain scores zero.
- Keep Knight Support the official application default and retain Classic through code, editor, and command-line settings. Preserve the configured ruleset through New Match and both restart paths. Resolve Knight Support on the whole post-action board before analyzing territory or publishing a snapshot. Keep CPU heuristics separate from authoritative resolution.
- When implementing main-phase rules, update the game design, session/public API docs, test coverage, and any affected architecture articles in the same change. Preserve opening-draft behavior and the common local/remote session direction.
- Follow [Predefined maps](Documentation/MapFormat.md) when editing built-in maps. Favor open squares and rectangles at least 8 × 8, varied rock formations, multiple attack routes, and draft positions across the interior and edges. Keep catalog design preferences separate from structural validation. Preserve exact retired layouts in the development-only `Benchmarks/Reference/Maps/` fixture collection and keep the catalog summary and validation tests in sync.
- Follow [CPU architecture](Documentation/CpuArchitecture.md) when changing CPU decisions. Keep the engine on the public snapshot boundary and verify originating session identity as well as round currentness when integrating asynchronous proposals.
- For search changes, charge each new authoritative pair to the same decision budget and preserve a comparable completed tier when deeper work stops. Verify terminal claims against every legal reply and compare production changes with frozen 8C on held-out maps.
- Follow [Strategic evaluation](Documentation/CpuStrategicEvaluation.md) for evaluator and simultaneous-policy experiments. Keep the frozen 8D.2 control independent of live tuning, separate outcome from margin, and keep geometry, player exchange and locked-health equivalents in the same solved-position split.
- Use [CPU tournaments](Documentation/CpuTournaments.md) for paired CPU experiments. Keep frozen opponents and historical fixtures independent of production tuning, preserve replayable histories, and keep generated tournament results in ignored output directories.
- Keep live and final territory scores on the same authoritative analysis. Use the board geometry for the score banner and retain both local input modes in runtime regression coverage.

- Follow [Small-board solver](Documentation/SmallBoardSolver.md) for exact simultaneous research. Keep the solver in Benchmarks and store generated tablebases and research runs under ignored exports/ or the external project-files directory.

- Follow [CPU opening strategy](Documentation/CpuOpeningStrategy.md) for draft changes. Use authoritative previews and compare draft policies with the same frozen Main policy on held-out maps.

- Keep the 8D.4 CPU baseline in its separate development assembly. Use the [8E calibration](Documentation/CpuDifficultyCalibration.md) and [battlefield audit](Documentation/BattlefieldBalance.md) when extending the ladder or map research. Keep generated maps and instrumentation out of ordinary gameplay builds.
